## Context

See `proposal.md` — Why. What shapes the approach is what is already on disk and may not be touched:

- `protocol/eventlog.py` folds an append-only log against a `Declaration` and is loud: an unknown
  event, an illegal transition, a missing required field or a malformed line raises `LogError`. It
  reads; it does not write.
- `protocol/backlog.py` declares the item — thirteen states, the event table, the required fields
  per event — and exposes readers (`frame`, `awaiting`, `lease`, `priority`, …).
- `protocol/turn.py` freezes the ledger row: four outcomes, `enforced_by`, `dirty`, `isolated`, a
  free-text `note`, and a rejection of home-rooted paths because the repository is public.
- `runtime/runs.py` writes the stream: `open_run` drops a `.start` marker, `append` writes the
  record once and never rewrites it, and a marker with no record reads back as a gap.
- `runtime/verify.py` gates `done`; `runtime/supervise.py` provides `single_flight` and `govern`;
  `runtime/config.py` reads the guardrail thresholds.
- The executor seam, `run(frame, workspace, limits) -> RunResult`, is owned by another worker and is
  not on disk yet.

Two facts about the existing code drive most of what follows. There is **no writer** for event logs
anywhere in the repository — only the fold. And `supervise.govern` currently writes a `TurnRecord`
itself, which this change assumes will become injectable; that edit belongs to the concurrent
executor change, not here.

## Goals / Non-Goals

**Goals:**

- One module, `runtime/turn.py`, that is readable end to end as the five steps.
- Every invariant enforced by code already written, not by code this change adds and not by the
  prompt.
- A skill file short enough that its length is checked by a test.
- The turn runnable in tests with no network, no API key, and no agent, by injecting a fake executor.

**Non-Goals:**

- A CLI surface beyond what invoking one turn needs.
- Any abstraction that anticipates a second executor, a second log kind, or a second turn type. The
  sweeper turn and the board adapter are named in the design record and are not prepared for here.
- Reusing `govern` to run the agent. The turn calls the executor seam; whether that seam uses
  `govern` internally is the executor's business.

## Decisions

### The turn is a function, and the module holds no state

`turn.py` exposes one entry point taking the repository root, an executor, and resolved guardrails,
and returning the `TurnRecord` it wrote. Everything else in the module is a helper called from it.

*Alternative rejected:* a `Turn` class holding the item, the workspace and the proposal across steps.
It reads well and it is the shape that grows a pipeline: once there is an object with phases, adding
a phase is the obvious edit. `S173` says there are no workflows, only functions, and the cheapest way
to keep that true is to leave nothing for a stage to attach to.

### The agent's channel is one file, and its path is supplied by the turn

The turn creates a scratch path outside the repository, passes it to the executor as part of the
frame, and reads it after the executor returns. The agent's entire contract is: write one JSON object
there.

*Alternative rejected:* parse the transcript. It makes the proposal a function of prose and would put
this change in the business of understanding agent output.

*Alternative rejected:* let the agent append to the item log directly. Then the invariants would be
enforced only if the agent chose to run the fold, which is enforcement-by-prompt in disguise.

The scratch path is outside the repository so a killed run cannot leave the tree dirty and fail
another worker's commit.

### Validation is by re-fold, and the write is the same operation as the check

Appending is: read the item's log, build the candidate line, write log + candidate to a temporary
file, fold that file, and only on success rename it over the item's log. A rejected proposal never
touches the item's log, which is what the spec's "leaves no trace" scenario tests.

This makes the fold the single definition of what is legal. This change adds no second copy of the
transition table, and the module is expected to contain no `if state == …` over item states at all.

*Note on atomicity:* rename is atomic, and the turn holds `single_flight`, so there is no reader that
can observe a half-written log on one machine. Across machines this is a claim the CAS push would
have to carry, which is why cross-machine operation is refused rather than approximated.

`event_id` is a UUID4 and `ts` is RFC3339 UTC. Both are generated by the turn, never by the agent:
they are what deduplication and replay order depend on, and an agent-supplied timestamp is a value
the fold trusts from the one component measured as unreliable.

### The turn writes the ledger row; the executor reports a process fact

`RunResult.outcome` answers "did the agent process run and produce a verdict". `TurnRecord.outcome`
answers "did the turn advance". The mapping, which lives in one function:

```
no item eligible, no agent run          -> nothing-ready
event appended, item advanced           -> advanced
event appended, item is now blocked     -> blocked
proposal missing, refused, or rejected  -> failed
executor reports the process failed     -> failed
gate refused a done                     -> failed
```

`enforced_by` is `agent` when the turn wrote a verdict the agent proposed, `harness` when the turn
wrote the record on the agent's behalf — a killed run, a missing proposal, a refused transition.

The record's `note` carries the item id and the reason, and is passed through the same home-rooted
path check the record already applies. Nothing else about the record shape changes; `protocol/` is
not touched.

*Consequence to hold onto:* `govern` must stop writing the record or accept an injected writer. Until
that lands, a turn that runs a real executor built on today's `govern` would produce two records.
Tests use the fake executor, so this change is testable before that one lands, but the live run is
not runnable until it does.

### Claim, act, record — two commits

Commit one is the claim: the `claimed` event, committed before the executor is invoked. Commit two
carries the outcome event and the ledger row. Both commit by explicit pathspec, and both are made by
the turn rather than by the agent.

Between them the agent runs and money is spent, so a crash there loses work while leaving state
consistent — `architecture.md` §4's stated and accepted failure mode. The claim carries `owner`,
`expires_at` and `attempt` because the item declaration requires them; nothing in this change
*reclaims* on expiry, and that absence is deliberate (see the proposal's non-goals).

*Alternative rejected:* one commit at the end. It is what `architecture.md` §4 shows to be the fault
that deletes a state: with a single commit, no observer ever sees `claimed`, and a crashed turn is
indistinguishable from a turn that never ran.

### Planning writes items; it does not act on them

A planning turn's proposal is a list of `created` events, one per new item, each carrying `loop` and
a frame with goal, method and assumptions. The turn writes each to `backlog/items/<id>.jsonl` and
stops. It does not then act on what it just planned: acting is the next turn's job, and the
acceptance criterion is precisely that the second turn picks that up from the repository alone.

Item ids are allocated by the turn, not by the agent, for the same reason `event_id` is not, and they
are generated **without reading anything**:

```
itm-<YYYYMMDD>T<HHMMSS>Z-<8 hex>        matching the question format already on disk
```

*Alternative rejected:* `itm-` plus a counter one above the highest id present. `S186` names why —
a field that requires reading the current maximum is not an identifier, it is a lock in disguise. Two
concurrent planning turns both read `itm-0007` and both write `itm-0008`, and with one file per item
that is either a clobber or two different items fused into one log by `merge=union`. Sortability is
the only thing lost, and nothing wants it: nothing in the design orders items by id, and the fold
already orders by `ts` and `event_id`.

*Deliberately not capped:* the number of items one planning turn may emit. A created item is inert
until a later turn claims it, so a runaway plan costs storage and noise rather than money, and there
is no traffic yet from which to choose a number. If it becomes a problem it will be a measured one.

### The skill file is short, and the test enforces it

The skill states where to write, what shape to write, and that it is one event. It does not restate
the transition table, the required fields, or the reasons. A test asserts the word count stays under
the bound.

Draft (the wording is settled in apply, the length is not negotiable):

```
Write exactly one JSON object to the path given as PROPOSAL_PATH, then stop.

  {"event": "<event name>", ...fields for that event}

One event. Do not set event_id or ts — the caller does. Do not edit any file
under backlog/. Do not decide what happens next; report what happened.

If you could not do the work, say so with a failure event rather than an
optimistic one.
```

*Why this is a rule and not a preference:* `S098` measured a 1,500-word prompt performing worse than
a 103-word one, and `S171` measured instruction dilution over a long run. The invariants are in the
fold, so restating them in the prompt buys nothing and costs adherence to what is left.

### Answers are applied at step one, by the turn

The turn scans `questions/` for questions that closed since the item was blocked and appends the
corresponding `unblocked` event, whose target state the fold reads from `awaiting.return_to` — stored
at block time, never recomputed. No steering inbox is read; the gap is recorded in the proposal.

## Risks / Trade-offs

- **`govern` writes a second record** → tests inject a fake executor, so this change lands and is
  verifiable independently. The live two-turn run waits for the executor change; the director
  sequences it. If that change does not land, the live run produces duplicate rows and must not be
  taken as the acceptance receipt.
- **The executor seam may not carry the frame the agent needs** (the proposal path, the skill
  selection) → the turn passes them inside `frame`, which the seam already accepts. If the real
  executor turns out to ignore or reshape `frame`, that is a report to the director, not a
  workaround here.
- **Cross-machine concurrency looks supported and is not** → the turn refuses to run when configured
  for it without the CAS push, so the failure is loud at the first attempt rather than silent at the
  first collision.
- **A killed turn leaves a `.start` marker and no record** → this is by design: `runs.read_window`
  reads that as a gap, which the stall detector already treats as `failed`. The turn does not clean
  markers up.
- **Item id allocation by scan is racy across machines** → same boundary as everything else here:
  safe under `single_flight`, refused across machines.
- **A test that fakes the executor proves the machinery, not the platform** → true, and stated so the
  acceptance receipt is not mistaken for a D014 receipt. D014 counts commits to `a2web`; nothing here
  starts that clock.
