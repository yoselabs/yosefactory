# a2sdlc V1.0 — first shippable cut

## Problem

The vision chain (`docs/vision/01`..`03`) is settled, but it describes 12–18
months of work. Nothing ships until we decide **what lands first**.

Without a hard V1.0 fence, three things go wrong: (a) the migration keeps growing
until the 4-week refactor becomes a 4-month rewrite; (b) near-term commitments
N1–N9 get partially-started in parallel and none finish; (c) we never earn the
first unit of real trust — "this engine ran a ticket on a real repo, in real CI,
end-to-end, repeatedly, without humans intervening between stages."

V1.0 exists to earn that trust on **one real repo, on one tracker, with one
stage chain**, behind the architecture the vision commits to. Everything else is
postponed — not cut from the vision, just not in the first box.

**Where the work happens.** All refactoring lands on a dedicated branch inside
`a2sdlc-engine`. The trust target — the repo the engine runs against end-to-end
— is `iorlas/a2sdlc-smoke`, the existing GH-adapter integration fixture.
Engine development and engine execution are two repos on purpose: the engine
refactors on one branch, the smoke target is the clean environment the engine
drives.

**V1.0 is private.** Not a public release. Onboarding flow exists (P-08) but
adoption is internal only — no Marketplace listing, no external install docs
push. Public release happens post-V1.0, once N9 full hardening ships.

Serves product principles P-06 (real-CI-integration grade), P-07 (built by
agents, for agents — 500 LOC hard cap, thin composition root), P-08 (5-minute
onboarding is the adoption gate).

## Appetite

**4–6 weeks**, single developer working with agent assistance. Fixed. Work that
doesn't fit gets cut to POSTPONED, not extended.

Reference: architecture vision §10 estimates 3–4 weeks for P1–P8 alone. V1.0
adds N1 (inline review), partial N4 (secrets scan only), N7 (QA layers L1–L6
lit), N8 (two Apps), and an interim N9 posture on top. 4–6 weeks is the stretch
target, not the expected case.

## Solution sketch

V1.0 is "the target architecture on the hot path, nothing else."

**Tracker / host:** GitHub Issues + GitHub repo is the **only tested** path.
**Jira + dispatcher is scaffolded but not tested in V1.0** — dispatcher
bounded context survives the refactor cleanly, `CompositionProfile` supports
the `workflow_input` ingress + `dispatcher_http` output subscriber slots, the
Jira `WorkAdapter` + translator stay wired. Full Jira end-to-end testing +
dispatcher service hardening is a separate follow-on effort. GitLab has no
shipping adapter in V1.0 — ships in the next version.

**Stages:** SPEC → IMPLEMENT → REVIEW → MERGE. The four current stages become
proper `StageHandler`s under the new architecture. No new stages.

**Architecture migration:** all eight phases (P1–P8) IN. P1+P2+P3 deliver the
load-bearing split (Event ADT, Stage handlers, Effects + interpreter); P4+P5+P6
collapse the composition root and kill the Mode 1/Mode 2 env-branch; P7+P8 are
rename + import-linter lockdown (1 day each — cheap closure).

**Near-term commitments in V1.0:**

- **N1 inline PR review** — IN. Without per-line comments, the REVIEW stage
  looks like a generic LLM wall of text, not a product. Lands with P2.
- **N4 partial** — IN for gitleaks / secrets-scan effect only. Full shift-left
  (trivy, semgrep, per-stage threat modeling) POSTPONED.
- **N6 architectural constraint** — IN. N6 = "every stage must be invokable
  standalone" (architecture vision §2.21a). Two sides:
    - **Architectural side (IN):** stage handlers don't assume prior-stage
      on-disk artifacts; the effects interpreter supports a "standalone" mode
      that no-ops transition effects but fires terminal effects. Free — it's
      a property of the P2 handler shape.
    - **Product side — partially IN:** `a2sdlc review <pr-url>` ships in V1.0
      as a single standalone CLI command. Reason: exercising the standalone
      interpreter mode once with a real command is the only way the
      architectural constraint stays honest over months — unused code paths
      rot. ~1 day on top of P2. `a2sdlc spec`, `a2sdlc implement`, and
      per-stage GitHub Actions packaging stay **POSTPONED** (marketing surface,
      no V1.0 trust value).
- **N7 QA layers L1–L6** — IN (unit, contract, fake-integration, real-platform
  nightly against fixture repo, event-replay corpus, L6 smoke release gate). L7
  eval harness scaffolded + one-stage pilot.
- **N8 two GitHub Apps** — IN. Required by the onboarding doc already.
- **N9 interim posture** — ADR-0006 drafted with trust boundaries + tool
  allowlists per stage + delimiter escaping for untrusted input. V1.0 is
  private-only, so public-repo exposure is not a V1.0 concern; full hardening
  ships before public release, post-V1.0.

**Out — explicitly postponed:** N2 subtasks, N3 worktrees, N5 backpropagation.
All DEPLOY / STALENESS_CHECK / EPIC_SHAPING / RELEASE_NOTES / SECURITY_SCAN /
REVERT stages. GitLab, Linear, ADO adapters. Subagents (Claude SDK flat event
stream work). Rate-limit park-and-sweep. Cancellation propagation.

**Jira dispatcher — special case: scaffolded, not tested.** The dispatcher
bounded context (`packages/dispatcher/`) + Jira `WorkAdapter` + `workflow_input`
ingress + `dispatcher_http` output subscriber all survive the refactor and
compile green. They are exercised at L1/L2 (unit + contract) but NOT at L4
(real Jira sandbox) or L6 (end-to-end smoke). Jira end-to-end lives in a
separate follow-on effort with its own fixture + its own success signal.

The dispatcher itself does **not need architectural revision** for V1.0 — the
vision §7.6 already specifies a separate bounded context with a thin wire
protocol (`WorkflowInputReader` + HTTP POST `/runs/{id}/events`). P1–P8
change how the engine *selects* the Jira mode (`CompositionProfile` kills the
`DISPATCHER_URL` env-branch) but the wire contract is stable. One ADR lands in
V1.0 to close Q1: **ADR-0007 — engine/dispatcher wire protocol**, formalizing
the two surfaces so the Jira follow-on has a contract to test against.

**Quality gates:** `make check` post-IMPLEMENT IN; diff-coverage IN (already
part of `make check` today); secrets scan IN; trivy/semgrep POSTPONED.

**Observability sinks:** MLflow IN; progress comment on ticket IN; GH Actions
log with agent prefix IN; rich console (local dev) IN; HTTP subscriber / web UI
/ OTEL / Datadog POSTPONED.

See RFC-0001 for the full scope matrix and per-item rationale.

## Rabbit holes

- **Migration creep.** P1–P8 touches every package. If we try to "just improve
  X while we're there," the 4-week plan becomes 10 weeks. Rule: each phase ships
  green, and nothing outside the phase's delta lands in that phase. No drive-by
  refactors.
- **N7 perfection.** The seven-layer QA strategy is aspirational at full depth.
  V1.0 ships with L1–L6 lit up against **one** fixture repo (iorlas/a2sdlc-smoke,
  already active per the GH adapter integration tier in CLAUDE.md). Token-matrix
  coverage beyond `ghs_` installation tokens — POSTPONED.
- **N8 branch-protection edge cases.** Two Apps + branch protection interact in
  non-obvious ways. Q12 (branch-protection fallback) must close with "PR ready,
  awaiting human merge" as the graceful degradation, not engine spin. Explicitly
  in scope as a Q12 close.
- **N9 scope explosion.** ADR-0006 could grow into a full threat-model document.
  Scope it to "attacker model + three concrete defense layers (tool allowlists
  per stage, delimiter escaping, effect-level gating on merge/label) + interim
  posture statement." Anything beyond that — a separate pitch post-V1.0.
- **Dogfood vs external trust signal.** The natural V1.0 target repo is
  iorlas/a2sdlc-smoke (the existing fixture). That earns engineering trust but
  not product-market signal. Product signal (§4.1: 100 repos, 60% of merged
  tickets) is a 12-month measure, not a V1.0 measure. Don't confuse them.
- **Composition profile surface.** The `CompositionProfile` is new in P6. It
  must be small enough to not be a second config surface users learn. Keep to
  `tracker / ingress / review / git / progress / middleware` slots — no more.

## No-gos

Things we will NOT do in V1.0 even if tempting.

- **No GitLab adapter**, no Linear, no ADO, no Forgejo. Adapter Protocols stay,
  but zero ship implementations beyond GitHub + local + (Jira dispatcher
  scaffolded-not-tested per §Solution sketch).
- **No new stages.** No DEPLOY, no STALENESS_CHECK, no EPIC_SHAPING, no
  RELEASE_NOTES, no SECURITY_SCAN stage, no REVERT stage.
- **No subtasks / epics / parent-branch merging.** N2 is architecturally
  reserved (parent_key/children fields in TicketState v2 already) but no
  orchestration code.
- **No backpropagation.** N5 stays RFC-blocked; schema placeholders stay empty.
- **No subagents.** Flat event stream design (§2.22) lives in the vision;
  implementation POSTPONED.
- **No rate-limit park-and-sweep.** Effect variant reserved; no scheduled
  workflow, no self-heal code.
- **No worktree isolation.** Single-worktree local mode is the dev loop.
  Parallel A/B by Denis continues to use `run_id` isolation without worktrees.
- **No per-stage CLI products.** `a2sdlc review` as a Copilot-alt product surface
  is post-V1.0. The architectural constraint (handlers not coupled) is enforced;
  the marketing / packaging surface is not.
- **No web UI.** Per product vision §9.3 — the tracker IS the UI. Don't even
  sketch it.
- **No managed SaaS, no auth, no multi-tenancy.** All explicit non-goals per
  vision §9.3.
- **No second agent provider.** Claude Agent SDK remains the only shipping
  `StageRunner`. Gemini / GPT / LiteLLM adapters — POSTPONED.

## Nice-to-haves

Cut first if appetite runs out. Listed in the order we'd cut them.

- **L7 eval harness pilot.** Scaffolded MLflow-based eval for one stage
  (SPEC) against fixture tickets. If appetite is tight, L7 becomes "scaffolded,
  not piloted" — Bet #2 signal comes post-V1.0.
- **Event-replay corpus seeding.** Capture 3–5 real GitHub webhook payloads per
  event type; bake into L5. If we only have time for label-trigger + PR-review
  payloads, that's fine.
- **Trivy / semgrep effect variants.** Registered in the effects ADT even if
  no interpreter arm ships — cheap forward compatibility.

## Success signal

V1.0 is shipped when **all of the following are true** on the iorlas/a2sdlc-smoke
fixture repo:

1. A new issue labeled `agent` drives a full SPEC → IMPLEMENT → REVIEW → MERGE
   cycle with zero human intervention between stages, running in real GitHub
   Actions against real GitHub APIs and real Claude.
2. The cycle completes cleanly ten times in a row across varied issue shapes
   (small bug, small feature, feedback loop that bounces REVIEW → SPEC).
3. The REVIEW stage posts line-level inline comments, not a single aggregate
   comment.
4. Branch protection on `main` is enabled on the fixture repo, and MERGE
   completes via the reviewer App's approval — no self-approval workaround.
5. `pipeline.py` composition root is ≤ 80 LOC. No a2sdlc file exceeds 500 LOC
   (agent-harness enforced). Import-linter passes with the new package layout.
6. The L6 smoke workflow is gating releases — tag cannot move without smoke
   green.
7. Onboarding a second copy of a2sdlc onto a fresh private GitHub repo takes
   ≤ 5 minutes of human effort, end-to-end, following `docs/onboarding.md`
   verbatim. (Sanity check on P-08 — not a public-release gate in V1.0.)
8. An eval on the SPEC stage runs `make eval` green against the pilot fixture
   set. "Green" = SPEC **output-quality** metrics (completeness /
   spec-coverage against fixture tickets) do not regress by more than the
   configured threshold (see OQ5) versus the last tagged engine version.
   This is about **stage output quality**, not engine code correctness —
   engine code correctness is covered by L1–L6.
9. ADR-0006 is Accepted with interim posture language.

When 1–9 hold, V1.0 ships. Post-V1.0 roadmap picks up N2 / N3 / N5, additional
trackers, additional stages.
